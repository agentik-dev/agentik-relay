# agent-relay design: the session layer is read only while fresh (r1)

**Status:** design r1, 2026-10-14, written before code and revised once after its one refuter round (§7), which passed with nine notes; the revision takes four of them. AR75 built §5 item 1; AR76 took three notes of its review (§2.4 for the relay's own state dir and the hooks', a moved config folder's reason, a null `inputs`). It amends relay-r1 §9 (configuration). The settled entry 10 (the repo's verify limit) is what this record makes reach a night; no entry of `DECISIONS.md` covers the session layer, and GUIDE §3 (agentik-commons; agentik-hq entry 6) puts it above the repo's files and leaves room for a further condition. The finding is `NICE_TO_HAVE.md`'s "A night takes a frozen session layer through tmux".

## 1. The problem

`ConfigPaths` (`internal/effects/config.go:73`) reads three layers, lowest first: the user's file, the repo's `.claude/agentik/config.yaml`, and, when `$CLAUDE_CODE_SESSION_ID` names a session, that session's `resolved.yaml`, written by the session plugin at its SessionStart and on `set`. The session plugin writes the file's `relay` section from the shipped and the user's profiles, the repo's `config.yaml`, its `config.local.yaml` and the launch profile (`claude_session/resolver.py:396-405`). Its overlay (`set`) feeds the `session` section only (`:407-415`). So the `relay` section is a copy of files, taken when the session started, and it sits above the repo's own layer.

A night started by a chain script in tmux inherits the id of the sitting that started it. On 2026-10-14 at 01:39 the consumer raised `verify_seconds` from 1800 to 3600 on main. The sitting that started night 2026-10-14-1 at 03:42 had resolved at 23:13 the day before, with 1800. The night cut a row's verify at 1800 (ledger `"cut":1800`, red `verify-cut`), and a hand gate went green in 17 minutes. Any night or verb run under a session older than a config edit reads the old values.

## 2. The decision

1. **The session layer is read only when it was resolved from the files the relay reads, as they are now.** GUIDE §3 has each resolved file list its inputs, `provider.inputs: [{path, sha256}]`, with `sha256` null for a file that was absent. `LoadConfig` reads that list from the layer file and reads the layer only when the list names the relay's own repo file and its own local file (§2.2), each at the sha256 that file has now; a null value matches only a file that is still absent, and a file that cannot be read for any other reason counts as changed. Paths compare after `filepath.Clean` only; a spelling through a symlink reads as another checkout, and the skip reads the same files. The other inputs (the profiles, the overlay) are not checked: the overlay feeds only the `session` section (`resolver.py:407-415`), and a profile edit reaches a live session's own keys no sooner.
2. **The relay reads `config.local.yaml` itself.** It is the third layer, between the repo's file and the session's: the `config.local.yaml` in the same folder as the repo file the relay picked (`.claude/agentik/`, else the old `.claude/claude-code-session/`), as the session plugin picks one folder for both (`resolver.py:113-115`), with its `relay` section, else `agent-relay`, read as the repo's file is. GUIDE §3 already lists this layer, and relay-r1 §9 leaves it out. Today it reaches the relay only through the session layer, so without it a skipped layer would drop a local value.
3. **A layer that cannot be shown fresh is not read.** A stale layer, one resolved for another checkout (a worktree's sitting lists that worktree's files), one with no `provider.inputs` list, or one with a malformed list is skipped whole, never in part. It is not listed in `Sources`. `Warnings` gains one line naming the layer and why, and doctor's config row reports it as a warning, never a failure.
4. **`$XDG_STATE_HOME` with a leading `~/`** is expanded under `HOME`, as the session plugin expands it, so both name one state dir.

With the layer fresh, every value is what it is today. With it skipped, the relay reads the same repo files itself, so only a profile's own `relay` keys are lost. The shipped profiles carry only `enabled`, `queue` and `merge` at the relay's own defaults, and the relay never reads `enabled`.

**Rejected.** Every input hashed as recorded (r1 before its refuter): the overlay is an input, and a sitting's first prompt rewrites it (§7, note 4), so every live sitting's layer would read stale, and an install of the session plugin replaces the profiles' path. The relay drops the session layer: GUIDE §3 binds it. A night's verbs skip the session layer: a hand `gate` from an older sitting is as stale, and the profile's keys would differ by verb. The session plugin writes only a session's own overrides: that changes GUIDE §3 for four plugins, and since the overlay cannot set relay keys, the relay's section would always be empty.

## 3. The seam and the record

- `internal/effects/config.go`: `ConfigPaths` gains the local layer, picked beside the repo file. One function decides whether the session layer is fresh, given the parsed file, the relay's repo and local paths, and `FS`. The strict YAML reader reads the `inputs` list from every real file (§7, note 7), and reads a null as the string `null`, which means absent; any other value that is not 64 lowercase hex digits is malformed. `FS` gains a read-and-hash only if it has none.
- No ledger key and no `--json` key changes. A night records nothing new: the repo's value wins, and the ledger's `cut` already says which limit ran.
- relay-r1 §9's configuration sentence names the four layers and the freshness rule.

Most are ended sessions, and any of them is the layer of a night its sitting starts.

## 5. The cut into packets

1. **AR75, the fresh session layer.** §2 and §3. Acceptance by named tests in `internal/effects`: a session layer that lists the relay's repo and local files at their current sha256 is read (its `verify_seconds` wins over the repo's), whatever its profile and overlay inputs hold; the repo file changed, a recorded-null local now present, or the repo file unreadable, leaves the layer unread, the repo's value in force, a warning naming that input, and the layer absent from `Sources`; a layer listing another checkout's repo file is unread with a warning; no `provider` block, or a malformed `inputs` (a sha256 that is neither null nor 64 hex), leaves it unread with a warning; a relative path in `inputs` is not checked; `config.local.yaml` is read between the repo's file and the session's, from the repo file's folder (an old-folder local beside a new-folder `config.yaml` is not read); `XDG_STATE_HOME=~/x` names `$HOME/x`; doctor's config row shows the warning and does not fail. The tests that plant a session file (`config_test.go:23`, `agentik_r1_test.go:58` and `:69`) give it a `provider.inputs` block.

## 6. Open risks

- **A profile edited during a session.** Its `relay` keys stay as the session resolved them, as the session's own keys do, until the next SessionStart or `set`. No profile carries relay keys beyond the relay's defaults today.
- **A running relay keeps what it loaded.** A night started before an edit runs on its start values, as it does for the repo's layer. Unchanged here.
- **Cost.** Each `LoadConfig` hashes two small files, once per verb that loads the configuration; `status --watch` never calls it (`cmd/agentik-relay/main.go:1418` goes to `night.Watch`). One `LoadConfig` with a fresh layer measured about 57 µs (AR75's review).
- **The other plugins.** decisions and respeak read the session layer under the same §3 and freeze the same way. One sentence in conventions §3 would bind them too. It is filed with the session plugin, not taken here.
